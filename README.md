# Plant Simulation: Pumps, Tanks, Valves, Pipes and Sensors

An industrial plant simulation that detects abnormal conditions and simulates operating changes.
It has a reproducible synthetic dataset, a three-tier web application, and a validation and test suite.

- **Seed:** `20261022`
- **Scale:** 3 facilities, 20 pumps, 30 tanks, 60 valves, 107 pipes, 100 sensors, 100,000 telemetry points
- **Stack:** React (Tier 1), FastAPI (Tier 2), SQLite (Tier 3)
- **Data:** fully synthetic, generated by code. No external data sources are used.

## Architecture (three tiers)

| Tier | Technology | Folder | Responsibility |
|------|------------|--------|----------------|
| 1. Presentation | React 19, TypeScript, Vite, recharts | `frontend/` | Shows data and sends requests. No business logic. |
| 2. Application | FastAPI | `backend/app/` | Routes, schemas, services, repositories |
| 3. Data | SQLite | `backend/plant.db` | Created from `data/seed`. Not committed to git. |

Inside Tier 2, each layer has one job:

- **Routes** receive the request, call a service and return the response. They contain no business logic.
- **Schemas** (pydantic) define the request and response shapes.
- **Services** hold all business rules: topology, detection, mass balance, simulation, alarm lifecycle, reports, metrics.
- **Repositories** are the only code that talks to the database. `plant_repo` is read-only.

Errors always use one format: `{"error": {"code", "message", "details"}}`
(`404 NOT_FOUND`, `422 VALIDATION_FAILED`).

The frontend has five tabs: Facilities, Telemetry chart, Alarms (run detection, acknowledge, clear, history),
Simulation form, and Data quality (including detection metrics). Each tab has loading, empty and error states.

## Setup (Windows PowerShell)

Needs Python 3.12 and Node.js.

```powershell

cd plant-sim\backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

uvicorn app.main:app --port 8000
```

`python -m app.init_db` creates `plant.db` and loads the CSV files from `data/seed`. The database file is
git-ignored, so run this once after cloning.

```powershell

npm install
npm run dev
```

Open http://localhost:5173. The API runs on port 8000, and CORS allows `localhost:5173`.

Other frontend scripts: `npm run build`, `npm run lint`, `npm run preview`.

## Generate the dataset

Run from the project root (the generator lives at the root, not in `backend`):

```powershell
python -m generator.build_dataset --seed 20261022 --out data/seed
```

This writes 13 files: one CSV per table, `seed.sql` (100,509 INSERT rows), ground truth (CSV and JSON, in
`data/ground_truth/`), `staging_edge_cases.json` and `manifest.json`.

| Item | Count |
|------|-------|
| Facilities / pumps / tanks / valves | 3 / 20 / 30 / 60 |
| Pipes / sensors | 107 / 100 |
| Telemetry points | 100,000 (100 sensors x 1,000 steps) |
| Operating modes / mode valve states | 9 / 180 |
| Ground-truth rows | 13 |

**Data dictionary:** [docs/data_dictionary.md](docs/data_dictionary.md). Column names carry their units
(for example `rated_flow_m3h`, `shutoff_head_m`, `capacity_m3`, `min_level_pct`), and every sensor row has a `unit` column.
IDs for pipes, operating modes, telemetry and alarms use assumed formats (PIPE-001, MODE-001, TEL-000001, ALM-000001),
marked as "assumed" in the dictionary.

**Source manifest:** `data/seed/manifest.json` lists every file with its row count and SHA-256 checksum, plus the seed.
`.gitattributes` keeps LF line endings so the checksums hold on every machine.

## Data design

1. A **valid baseline** is generated first (pump curves, tank levels, valve flows, sensors, operating modes).
2. **Labelled anomalies** are injected into telemetry (8 timed scenarios).
3. The **5 required edge cases** are kept in `staging_edge_cases.json`, outside the normal telemetry table.
4. The **ground truth** (13 labelled scenarios: 8 timed scenarios + 5 edge cases) is stored in its own folder,
   `data/ground_truth/`. It is read through `ground_truth_repo`, which the detection-metrics endpoint uses to
   score alarms. It is not a detector input.

## The five edge cases

| ID | Edge case | How it is caught |
|----|-----------|------------------|
| EDGE-001 | Pipe `PIPE-901` points to missing node `VALVE-999` | Pipe validator and topology service |
| EDGE-002 | Tank level 112.5% (capacity is 100%) on `SNS-001` | Tank-reading validator. Live detector: see note below |
| EDGE-003 | Flow conservation violated: 500 m3/h in, 380 m3/h out, residual 115 vs tolerance 10 | Flow-balance validator and balance service |
| EDGE-004 | Simulation `SIM-2026-900001` has no input configuration (`mode_id` is null) | Simulation validator and simulation service |
| EDGE-005 | Sensor `SNS-031` fault labelled as a process fault | Fault-label rule: if only one related sensor deviates, it is a sensor fault |

EDGE-002 is staged outside the telemetry table as a single reading, so the live detector does not score it.
The overflow rule is unit-tested separately and needs 3 consecutive readings above 100%.
EDGE-005 shows as detected in the live metrics only because the real scenario SCN-007 (sensor fault on SNS-031) matched.

## Detection rules

- Deviation: more than 6% from expected for 5 or more readings.
- Stuck sensor: 8 identical readings in a row.
- Overflow: 3 consecutive tank readings above 100%.
- Mass balance: |inflow - outflow - storage change| must stay within tolerance.
- Fault classification: both related sensors move = process fault; only one moves = sensor fault.

Alarms are raised by `POST /detection/run`. They can be acknowledged and cleared, and every change is kept in a
history table (history is never overwritten).

## Simulation

Each simulation run needs an operating mode (`mode_id`) as its input configuration. A run stores its mode,
assumptions, seed and result, so it can be repeated. Outflow is calculated as inflow x average valve position
(a deliberate simplification).

## Measured detection metrics

`GET /metrics/detection` on this dataset: 8 timed scenarios, 8 detections. Matching rule: same component,
same alarm type, overlapping time.

| TP | FP | FN | Precision | Recall | F1 | Mean delay | Max delay |
|----|----|----|-----------|--------|----|------------|-----------|
| 8 | 0 | 0 | 1.0 | 1.0 | 1.0 | 7.8 min | 16.0 min |

**This is a small sample, and the detection thresholds were tuned on this same seed**, so the perfect scores
should not be read as general performance. EDGE-001, EDGE-003 and EDGE-004 are checked by the topology, balance
and simulation services and are listed as "not scored here".
